# Release manifests

Every published CrossMix-OS SE surface (image, hotfix) ships with a JSON manifest that ties the
published bytes back to a commit, to the inputs the build consumed, and to the transformations the
build applied. The manifest exists so the distribution can be audited and measured without running
anything from it.

The generator is [`.github/scripts/release-manifest.sh`](../.github/scripts/release-manifest.sh)
(POSIX `sh`, no dependencies beyond `sha256sum`, `awk`, `find`). It is kept under `.github` on
purpose: the packaging step deletes `.github`, so the tool can never leak into the SD payload.

## Where manifests come from

| Surface | Published as | Produced by | Scope |
| --- | --- | --- | --- |
| `image` | release asset `CrossMix-OS_v<version>.manifest.json`, next to the `.7z` (or `.7z.001`, `.7z.002`, …) | `Publish release manifest` step, after the archive exists | whole payload tree |
| `hotfix` | workflow artifact `release-manifest-v<version>` | `Generate hotfix surface manifest` step, before cleaning | `_assets/hotfixes` only |
| `kit` | nothing automatic | run by hand | an explicit `--include` selection |

A `kit` is a selection of paths, not an image. The generator enforces this: `--surface image`
rejects `--include`, and `--surface hotfix|kit` refuses to run without one.

Both the image and hotfix manifests are also uploaded as the workflow artifact
`release-manifest-v<version>`, so an audit still has them if the release upload fails.

## Reading a manifest

```console
$ jq '{version: .release.version, files: .totals.file_count,
       bytes: .totals.logical_bytes, artifact: .artifacts[0].name}' \
    CrossMix-OS_v1.4.0-ce.2.15.manifest.json
```

Top-level keys:

| Key | Meaning |
| --- | --- |
| `schema` | `crossmix-release-manifest/1`. Bumped when a field changes meaning. |
| `surface` | `image`, `hotfix` or `kit`. Never infer "image" from a file list. |
| `release` | `version`, `tag`, `commit`, `generated_at`, `generator` + its `sha256`, and `selection` (empty for an image). |
| `pipeline` | Repository, workflow path, `workflow_sha256`, `ref`, `run_id`, `run_url`. Packaging deletes the workflow file, so its hash is captured before cleaning. |
| `tree` | `state` (`pre-transform`, `post-transform`, `mixed`), `hidden_file_count`, `listing_sha256`. |
| `totals` | `file_count`, `logical_bytes` (sum of file sizes), `artifact_bytes`/`artifact_count` (compressed archive, `null` when no artifact was hashed), `git_object_bytes` (+ status). |
| `files` | One entry per file: `path`, `size`, `sha256`. Sorted by path. |
| `transformations` | What the build does to the tree, and whether this tree shows it. See below. |
| `inputs` | Pre-transform inputs recorded before packaging destroyed them: the core `.7z` archives (with member counts when 7z is available), the firmware split volumes, `MinFwVersion.txt`. |
| `components` | Distributed areas with their license status. See below. |
| `artifacts` | Published archives: `name`, `bytes`, `sha256`, `compression`. |
| `warnings` | Facts that weaken the manifest: sparse checkout, version-stamp mismatch, files matching no component scope. |
| `notes` | Free-form `--note` values. |

`listing_sha256` is the sha256 of the `sha256⇥size⇥path` lines, in path order. Two builds of the
same payload produce the same value regardless of timestamps, so it is the fingerprint to compare
between releases.

Three byte counts are reported separately and must not be added together:

* `totals.logical_bytes` — bytes of the unpacked payload (what lands on the SD card).
* `totals.git_object_bytes` — physical size of the tagged tree's git blobs, measured before packaging.
* `totals.artifact_bytes` — compressed `.7z` size, i.e. what a user downloads.

## Transformations

`transformations[]` is generated by the pipeline's own steps, not by hand:

| id | action | Effect |
| --- | --- | --- |
| `delete-gitkeep` | delete `**/.gitkeep` | empty-directory placeholders never ship |
| `remove-assets-dir` | delete `_assets/` | readme images and hotfix sources are repository-only |
| `remove-license-file` | delete `LICENSE` | the GPL-3.0 text lives in the repository, not on the SD card |
| `remove-readme` | delete `README.md` | repository documentation |
| `remove-vcs-and-workflow` | delete `.git`, `.github` | VCS metadata and CI (including this generator) |
| `stamp-version` | write `System/usr/trimui/crossmix-version.txt` | the payload carries the version it was built from |
| `extract-core-archives` | extract `RetroArch/.retroarch/cores/*.7z` | five cores are shipped compressed and unpacked before packaging |
| `create-default-config-archive` | create `RetroArch/default_config.7z` | `retroarch.cfg` + `config/*`, restorable defaults |
| `include-hidden-entries` | include `**/.*` | packaging uses `dotglob`, so dotfiles are inside the archive |
| `package-7z` | create the release archive | `7z -mx=7`, split into volumes above the 2 GiB asset limit |
| `validate-firmware-payload` | validate `MinFwVersion.txt` vs payload | flashing fails on device if the declared firmware is missing |

`observed` is a measurement of the tree that was passed in, not a promise:

* `applied` — the effect is visible here (target absent, archive present, artifact hashed).
* `pending` — the target is still there; the tree is pre-package.
* `mismatch` — version stamp disagrees with `--version`.
* `not-observed` — nothing to measure (e.g. no core archive and no `--inputs` recording).
* `not-evaluated` — the check could not run (e.g. `MinFwVersion.txt` absent).

`tree.state` is decided only from unambiguous post-packaging markers (matching stamp, generated
`default_config.7z`, absence of compressed cores). A tree that never carried `_assets` is not
automatically "post-transform", so removals alone never decide the state.

## Licenses

Each `components[]` entry has `license`, `license_source`, `license_evidence` and `license_note`.

* `license_source: "declared"` — the repository states it. Only `crossmix-se` and `hotfix-payload`
  use this, citing `LICENSE` (GPL-3.0, same as upstream) and `README.md`.
* `license_source: "tree-evidence"` — the value was read from a license file *inside* the
  component's own paths (`LICENSE`, `COPYING`, `*licence*`, `NOTICE`, …) and classified from its text.
* `license: "MIXED"` — several different licenses were recognised inside one component; read the
  evidence list before drawing conclusions.
* `license: "DESCONOCIDA"` — **unknown**. No license file inside that component's paths, or the file
  present could not be classified. It is not a claim that the component is unlicensed; it is a
  claim that this tree does not prove a license.

`DESCONOCIDA` is deliberately the default for third-party payloads: emulator binaries (`Emus/`),
the five libretro core archives, BIOS dumps, bundled ROMs, the TrimUI firmware payload, and
themes/artwork. The repository's own GPL-3.0 does not automatically cover those pieces, and the
manifest never fills a gap with an assumption.

Two consequences worth knowing:

* `LICENSE` is deleted from the payload, so the GPL-3.0 terms travel only with the repository;
  `crossmix-se` says so in `license_note`.
* `distributed` is true when the component is part of the payload of the surface being described;
  `in_image_payload` says whether it belongs to the image specifically. A hotfix component is
  `distributed: true` with `in_image_payload: false`.

## Regenerating a manifest

```console
# Image, on a full checkout of the tag (post-packaging tree)
.github/scripts/release-manifest.sh \
  --tree . --version 1.4.0-ce.2.15 --tag v1.4.0-ce.2.15 \
  --commit "$(git rev-parse HEAD)" \
  --artifact ../CrossMix-OS_v1.4.0-ce.2.15.7z \
  --output /tmp/manifest.json

# Pre-transform inputs, before cores are extracted
.github/scripts/release-manifest.sh --tree . --record-inputs /tmp/inputs.tsv

# A hotfix payload is its own surface
.github/scripts/release-manifest.sh --tree . --version 1.4.0-ce.2.15 \
  --surface hotfix --include _assets/hotfixes --output /tmp/hotfix.json

# Reproducible run: pin the timestamp
.github/scripts/release-manifest.sh --tree . --version 1.0.0 \
  --generated-at 2026-01-01T00:00:00Z --output /tmp/a.json
```

Exit status 1 means bad usage or a missing path; the generator never writes a partial manifest
silently. `jq -e . manifest.json` must succeed before anything is published.

## Verifying a download

```console
# The archive hash in the manifest must match the file you downloaded
sha256sum CrossMix-OS_v1.4.0-ce.2.15.7z
jq -r '.artifacts[] | "\(.sha256)  \(.name)"' CrossMix-OS_v1.4.0-ce.2.15.manifest.json

# The payload hash must match a file inside the extracted image
jq -r '.files[] | select(.path == "System/usr/trimui/crossmix-version.txt")
       | "\(.sha256)  \(.size)"' CrossMix-OS_v1.4.0-ce.2.15.manifest.json
sha256sum System/usr/trimui/crossmix-version.txt   # after extracting the image
```

## What a manifest does not prove

* It describes a **tree**, not a physical SD card. Nothing here measures what is actually written
  on a user's card; that number is never filled in with an estimate.
* `DESCONOCIDA` is not a legal conclusion, and `GPL-3.0` on one component says nothing about its
  neighbours.
* A manifest generated from a sparse or partial checkout is incomplete. The generator warns
  (`sparse checkout: …`) and never claims to describe a commit it could not read.
